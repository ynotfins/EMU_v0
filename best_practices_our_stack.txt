Here are the best practices for your Next.js 14 stack, focusing on the App Router paradigm.

This stack is powerful. The core architectural principle is to use Next.js Server Components and Server Actions for all server-side logic (data fetching, auth, mutations) and confine Firebase's client-side SDKs to Client Components ('use client') for UI interactivity and real-time updates.

🌎 1. Project Structure & Core Setup (Next.js, TS, Tailwind)
Project Root: Use the src/ directory. This cleanly separates your application code from root configuration files.

/src
  /app
  /components
  /lib
  /hooks
/public
next.config.mjs
tailwind.config.ts
tsconfig.json
Next.js 14 (App Router):

Server Components by default: All components inside src/app are Server Components. Use them for data fetching and logic that shouldn't be exposed to the client.

Client Components ('use client'): Only add this directive to components that need client-side interactivity (e.g., useState, useEffect, onClick).

Colocation: Place components, tests, and related logic in the same folder as the route that uses them. For shared components, use src/components.

TypeScript:

Enable typedRoutes: true in your next.config.mjs for type-safe navigation.

Define types for your Firestore documents in a central src/lib/types.ts file and reuse them across your app.

Tailwind/shadcn/ui:

shadcn/ui is the right choice. It's not a component library; it's a collection of reusable components you own.

Installation: Initialize it with the npx shadcn-ui@latest init command.

Component Folder: Point the CLI to src/components/ui.

Utils: shadcn creates a src/lib/utils.ts with a cn (classnames) function. Use this everywhere to merge and conditionally apply Tailwind classes.

🔥 2. Firebase: Architecture & Environment
The most critical best practice is separating the Client SDK from the Admin SDK.

Environment Variables (.env.local):

Client Vars: Prefix all keys for the client-side SDK with NEXT_PUBLIC_. These are embedded in the browser's JavaScript.

Server Vars: All other keys (for the Admin SDK) are private and only accessible on the server (in Server Components, Server Actions, and API Routes).

Code snippet

# 1. Client SDK (browser-safe)
NEXT_PUBLIC_FIREBASE_API_KEY=...
NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN=...
NEXT_PUBLIC_FIREBASE_PROJECT_ID=...
NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET=...
NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=...
NEXT_PUBLIC_FIREBASE_APP_ID=...
NEXT_PUBLIC_GOOGLE_MAPS_API_KEY=...

# 2. Admin SDK (server-only, KEEP SECRET)
FIREBASE_ADMIN_PROJECT_ID=...
FIREBASE_ADMIN_CLIENT_EMAIL=...
# Store the private key as a single-line string with escaped newlines (\n)
FIREBASE_ADMIN_PRIVATE_KEY=...
Firebase Initialization:

Client SDK (src/lib/firebase-client.ts): Initialize the client app. This is used in Client Components.

TypeScript

import { initializeApp, getApps, getApp } from "firebase/app";
import { getAuth } from "firebase/auth";
import { getFirestore } from "firebase/firestore";

const firebaseConfig = {
  apiKey: process.env.NEXT_PUBLIC_FIREBASE_API_KEY,
  authDomain: process.env.NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN,
  // ...other NEXT_PUBLIC_ vars
};

// Initialize Firebase for client-side
const app = !getApps().length ? initializeApp(firebaseConfig) : getApp();
const auth = getAuth(app);
const db = getFirestore(app);

export { app, auth, db };
Admin SDK (src/lib/firebase-admin.ts): Initialize the admin app. This is used in Server Actions/Components.

TypeScript

import { initializeApp, getApps, getApp, cert } from "firebase-admin/app";
import { getAuth } from "firebase-admin/auth";
import { getFirestore } from "firebase-admin/firestore";

const serviceAccount = {
  projectId: process.env.FIREBASE_ADMIN_PROJECT_ID,
  clientEmail: process.env.FIREBASE_ADMIN_CLIENT_EMAIL,
  // Replace escaped newlines before parsing
  privateKey: process.env.FIREBASE_ADMIN_PRIVATE_KEY?.replace(/\\n/g, '\n'),
};

// Initialize Firebase for server-side
const adminApp = !getApps().length
  ? initializeApp({ credential: cert(serviceAccount) })
  : getApp();

const adminAuth = getAuth(adminApp);
const adminDb = getFirestore(adminApp);

export { adminApp, adminAuth, adminDb };
🔐 3. Firebase Authentication
This is the modern, secure pattern for the App Router. Do not use onAuthStateChanged for route protection. Use server-side session cookies.

Client-Side Sign-in: Use the Client SDK in a Client Component (e.g., LoginButton.tsx) to handle the popup/redirect.

Server Action: After a successful sign-in, the client gets an ID token. Immediately send this token to a Server Action.

Create Session Cookie: The Server Action uses the Admin SDK to verify the ID token and create a secure, httpOnly session cookie.

Middleware Protection: A src/middleware.ts file runs on the server for every request. It checks for the session cookie. If the cookie is missing or invalid, it redirects the user to /login.

Best Practice: Use a library like next-firebase-auth-edge or firebase-session-cookie to handle the cookie creation and middleware verification. Manually managing this is complex.

Your middleware (src/middleware.ts) will look something like this:

TypeScript

import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'
export async function middleware(request: NextRequest) { const session = request.cookies.get('session')?.value;

// 1. Verify the session (e.g., using adminAuth.verifySessionCookie) const isAuthed = session && (await verifySession(session));

// 2. Redirect if not authenticated and trying to access a protected route const isAccessingProtected = request.nextUrl.pathname.startsWith('/dashboard'); if (!isAuthed && isAccessingProtected) { return NextResponse.redirect(new URL('/login', request.url)); }

// 3. Redirect if authenticated and trying to access login if (isAuthed && request.nextUrl.pathname.startsWith('/login')) { return NextResponse.redirect(new URL('/dashboard', request.url)); }

return NextResponse.next(); }

export const config = { // Match all routes except for static files and API routes matcher: ['/((?!api|_next/static|_next/image|favicon.ico).*)'], };

🗃️ 4. Firestore & Realtime DB
Server Components (Default):

Use the Admin SDK (adminDb) for all one-time data fetches (getDoc, getDocs).

Fetch data directly inside your async Server Components.

Vercel Caching: Vercel aggressively caches Server Component fetches. To ensure you get fresh data from Firestore, either:

Use export const dynamic = 'force-dynamic' at the top of your page.

Use revalidateTag or revalidatePath after mutations.

Pass cache: 'no-store' to fetch (if using Next.js API routes).

Client Components (Real-time):

onSnapshot (Realtime DB & Firestore) is client-side only. It requires useEffect and useState.

Pattern:

Create a Server Component that fetches the initial data (using adminDb).

Pass this initial data as a prop to a Client Component.

The Client Component uses useState to hold the data and useEffect to attach an onSnapshot listener (using the Client SDK, db) to get real-time updates.

📦 5. Firebase Storage
Best Practice: Never upload directly from the client using the default SDK methods. Use signed upload URLs generated by a Server Action.

Client Component: The user selects a file. The component calls a Server Action, passing the file's name and type.

Server Action:

Uses the Admin SDK (getStorage()) to generate a v4 signed URL for PUT operations.

Applies any security logic (e.g., "is this user allowed to upload here?").

Returns the signed URL to the client.

Client Component: Uses a simple fetch (or axios) to PUT the file directly to the signed URL received from the Server Action.

Security Rules: Your Storage rules should then only allow writes if the user is authenticated, or even better, check for Custom Claims (e.g., request.auth.token.organizationId) that you set on the user via the Admin SDK.

🔔 6. Firebase Cloud Messaging (FCM)
FCM requires a service worker to handle background notifications.

Service Worker File: Create your firebase-messaging-sw.js file and place it in the public/ directory.

This file must also initialize Firebase (using initializeApp with the NEXT_PUBLIC_ keys).

This file will handle the onBackgroundMessage event.

Registration: In a Client Component (e.g., inside a useEffect), register the service worker:

TypeScript

if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/firebase-messaging-sw.js')
    .then(registration => {
      // Use this registration to get the FCM token
    });
}
Token Management: Get the FCM token from the client and save it to the user's document in Firestore (use a Server Action for this).

☁️ 7. Firebase Functions vs. Vercel Functions
Since you are deploying to Vercel, your "serverless functions" are your Next.js Server Actions and API Routes.

Use Next.js Server Actions for all logic triggered by your frontend (e.g., form submissions, auth, data mutations). Vercel deploys these as serverless functions automatically.

Use Next.js API Routes (src/app/api/.../route.ts) for webhooks or endpoints called by third-party services.

Use Firebase Functions only for Firebase-native triggers.

Example: functions.firestore.document('...').onCreate(...) to run logic when a document is created.

Example: functions.storage.object().onFinalize(...) to create a thumbnail when a new image is uploaded to Storage.

🗺️ 8. Google Maps
This is straightforward and client-side only.

Package: Use @react-google-maps/api.

API Key: Store it in .env.local as NEXT_PUBLIC_GOOGLE_MAPS_API_KEY.

Implementation: Wrap your map component (which must be a Client Component) with the <LoadScript> provider, passing it your API key.
